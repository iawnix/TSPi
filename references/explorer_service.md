# TS Hypothesis Explorer Service

Use this optional web service for local visualization of any TS-search
hypothesis workspace managed by `transition-state-workflow`. Keep the service
code in the skill and pass each project only as `--source`; the explorer must
not pollute the calculation workspace.

## Deployment Model

Remote compute stays remote:

```text
remote compute node
  /remote/path/tssearch_<system>/

local machine
  mirrors/tssearch_<system>/       # synced read-only source for explorer
  explorer_state/<system>/         # explorer cache, server metadata, layout
```

The explorer is one persistent service for all TS searches, not one service
per task. Start it once with no source arguments and keep it running:

```bash
python scripts/ts_explorer_server.py serve --host 127.0.0.1 --port 8765
```

With no `--source`/`--workspace-registry`/`--workspace-root`, it serves the
persistent registry at `~/.codex/state/ts_explorer/workspaces.json` and
**hot-reloads it on change**. Register a workspace explicitly during
`init_workspace` with
`--explorer-register` or `--explorer-registry <path>` so new searches appear in
the running service without a restart. A registered workspace whose source is
missing or mid-sync is skipped with a warning instead of killing the service.

Single-source mode remains available for quick one-off checks:

```bash
python scripts/ts_explorer_server.py serve \
  --source /local/mirrors/tssearch_group5 \
  --state-dir /local/explorer_state/group5 \
  --host 127.0.0.1 \
  --port 8765
```

New workspaces created by `scripts/ts_workspace.py init_workspace` write
`reports/explorer_launch_checklist.md` describing this persistent-service
workflow. By default, `init_workspace` does not write the persistent registry; pass
`--explorer-register` to use the default registry or `--explorer-registry
<path>` to use a non-default registry.


## Workspace Registry

`~/.codex/state/ts_explorer/workspaces.json` is the persistent registry; the
running service re-reads it whenever its mtime changes:

```json
{
  "schema": "ts-explorer-workspaces",
  "workspaces": [
    {
      "id": "group5-test2",
      "name": "Group5 TEST2",
      "project_dir": "/home/iaw/Codex/Project/2026-06-05/group5-test2-ts-search",
      "source": "/home/iaw/Codex/Project/2026-06-05/group5-test2-ts-search/local_mirror/tssearch_group5_m1_doublet_tree",
      "state_dir": "/home/iaw/Codex/Project/2026-06-05/group5-test2-ts-search/local_explorer_state"
    }
  ]
}
```

Each workspace should point at one synced `tssearch_*` directory. The service
exposes `/api/workspaces` and scoped routes under `/api/workspace/<id>/...`.
The registry is not a current-view store: in multi-workspace mode
`/api/workspaces` must not force a server-side `default_workspace`. Browser
clients choose the current workspace with URL `?workspace=<id>` first and
browser `localStorage` second. Single-workspace routes such as `/api/job` and
`/api/tree` are legacy conveniences for one configured workspace; in
multi-workspace mode they must return `workspace_required` and callers must use
the scoped routes.

## Zero-Pollution Rules

- `--source` is read-only.
- `--state-dir` must be outside `--source`.
- Do not write `.web`, cache, layout, logs, or UI metadata into
  `tssearch_<system>/`.
- Node layout, caches, and server metadata belong only under `--state-dir`.
- The service should tolerate temporarily incomplete synced JSON and report
  read errors instead of modifying source files.
- First release is view-only: no branch creation, evidence edits, or remote job
  execution from the browser.

## Sync Guidance

Prefer pulling from the remote calculation directory into a local mirror.

Start with metadata and small artifacts:

```text
manifest.json
tree.json
mechanism_model.json
knowledge_base.md
evidence_registry.json
pathway_model.json
nodes/**/node.json
nodes/**/hypothesis.md
nodes/**/decision_card.md
nodes/**/reflection.md
nodes/**/parsed/**
nodes/**/*.xyz
```

Avoid default sync of large scratch files, checkpoints, wavefunction files, and
unbounded trajectories. Sync Gaussian `.out` files only when the UI needs to
display them, or prefer parsed summaries.

Remote writers should use atomic updates for JSON: write `file.tmp`, then rename
to the final path.

## UI State Model

The explorer reads a normalized `ts-explorer-graph` payload generated by
`scripts/ts_normalize_view.py`. The browser should not infer chemistry validity
from raw `tree.json` / `node.json` fields.

State rendering is server-owned. Each normalized node carries two presentation
layers:

- compact card fields: `card_status`, `card_phase`, `card_label`,
  `card_line`, `card_severity`, and `card_color`, rendered as
  `Status[Phase]` labels such as `Success[Endpoint]` or `Error[Candidate]`;
- audit fields: `node_state`, `state_label`, `state_line`, `severity`, and
  `color`, derived from public `phase`, `node_disposition`, evidence, and
  closure data.

Derived `claim_status`, `outcome`, and `run_state` remain in the normalized
payload for audit, but they are not stored source-of-truth fields in `node.json`
and they do not have separate user-facing label systems. The payload includes
`presentation.card_status`, `presentation.card_phase`, and
`presentation.node_state` for the full presentation vocabulary. The UI renders
these fields verbatim and keeps no state-to-label or state-to-color maps of its
own, so state-model changes cannot drift from what the browser shows.

The explorer shows:

- mechanism model, open questions, and structured `mechanism_analysis` layers
  including source/evidence-backed reaction type, reaction-center, electronic,
  orbital, and energy records;
- pathway progress when `pathway_model.json` is present, so a partial multi-step
  pathway is not displayed as a complete workspace merely because one elementary
  step has an accepted TS;
- hypothesis tree nodes and parent-child branch edges;
- dependency edges from `input_refs` for multi-input operations such as QST2
  while preserving one primary `parent_id` lineage;
- backtrack edges from canonical `backtrack_events[]`;
- display-only replacement edges from a backtrack event's `from_node` to its
  `new_branch_node`, so a failed branch visibly points to the replacement
  branch while the canonical rollback edge still points to `to_node`;
- separate derived `lifecycle_state`, `run_state`, `claim_status`, `outcome`,
  `outcome_code`, and `claim_level`;
- active, stopped, ambiguous, rejected, numerical-failure, and accepted nodes
  without collapsing administrative stops into chemical failures;
- node tabs for Summary, Rationale, Timeline, Evidence, Reflection, Files, and
  JSON;
- validator warnings from `scripts/ts_workspace.py validate_workspace` when source
  artifacts are inconsistent.

The left sidebar should show task/job context, not duplicate the workspace
switcher. The topbar workspace chip is the canonical multi-workspace switcher.

Node detail payloads may include `file_notes[]` from the server. Render these
above the Files list to explain expected-but-unsynced artifacts such as
Gaussian `%chk`/`%oldchk` checkpoint files in remote run directories.

Fields such as `status`, `failure_type`, `backtrack_target`,
`backtrack_edges`, and `branch_decisions` are invalid in the runtime UI state
model. `graph.accepted_ts` is only the current accepted-node index; workspace
badges must use the pathway-aware `claim_state` emitted by the service.

## Validation And Normalization

Use these skill scripts instead of one-off task-local Python when preparing data
for the explorer:

```bash
python scripts/ts_workspace.py validate_workspace --root /local/mirrors/tssearch_group5 --pretty
python scripts/ts_normalize_view.py --source /local/mirrors/tssearch_group5 --pretty
```

Validation is read-only. It reports tree/node drift, missing node JSON,
inconsistent frontier/closed/accepted indexes, missing evidence files, invalid
old state fields, invalid backtrack event states, and malformed backtrack
references.

Normalization is also read-only. It emits only the current normalized fields. It does not
read, infer from, or output old state aliases, and it rejects backtrack events
outside the canonical `active` / `resolved` / `superseded` lifecycle.
