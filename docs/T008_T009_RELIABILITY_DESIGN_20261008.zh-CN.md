# t008 / t009 可靠性修复设计建议

状态：实现已落地；本文件保留原始设计理由和范围。实现、测试及明确限制见 [实施记录](RELIABILITY_REQUIREMENTS_IMPLEMENTATION.zh-CN.md)。对应 t008、t009 的原始源码基线为 `75afda55`。

## 目标与边界

保留 ResearchMap 为唯一规范研究状态，复用 Node、Claim、Gate、Attempt、Artifact 和事务边界。补全用户交付要求与执行证据之间的约束，不另建工作流引擎，不把所有研究固定为某种计算流程。

现有问题不是没有校验，而是校验的对象主要由 Agent 自己定义：可以遗漏依赖、把验收写成报告说明、关闭未执行节点，再把不存在的执行工作从派生义务中消掉。需要分别处理任务建模、领域验证、执行接口和真实能力缺口。

## 1. 用户交付要求与研究计划分离

在 ResearchMap 增加小型 `requirements` 集合，表达本次用户要求的交付，而不借用科学 Claim。Claim 可以被证伪，用户要求应被履行或明确保留为未履行。

建议最小记录包含：`id`、`source_ref`、`statement`、`constraints`、`acceptance_profile_ref`。字段名与合同版本在实现阶段确定。

- `source_ref` 绑定 Host 持久化的真实用户消息；来源真实性由 Host 验证，不采信 Agent 自报“用户已同意”。
- 明确区分用户给定的参数与 Agent 提出的研究方案。t009 的 local、M062X/6-31G**、相应程序核数和异构体研究范围是要求；TS 搜索方法和分支顺序是可调整方案。
- 验收 profile 是化学扩展中带版本的、可执行的有限检查集合，描述应具备什么证据，不规定唯一执行顺序，也不引入模型自由编写的规则语言。
- Node/Gate 引用对应 requirement；允许多个节点共同贡献证据，也允许复用已存在且验证过的证据。
- 覆盖和满足状态从绑定、Gate 和回执派生，不增加另一份可以独立修改的完成状态。

阶段节点完成只表示该节点的交付物已完成。例如输入准备节点可以在 TS 计算之前关闭；不能要求每个阶段完成整个机制研究。最终 requirement 的满足必须汇总其所需证据，不能简单等同于“关联节点均关闭”。

现有 `_research_obligations()` 改为同时投影未满足的 requirements。关闭或替换节点不能让用户交付义务消失；尚未分配执行节点的要求明确显示为未覆盖。

需要承认：任意自然语言需求的完整抽取无法由 Schema 保证。初始计划应保留逐项来源并输出覆盖摘要，配合独立于执行计划生成的覆盖审查；它可以自动执行，不要求每一步人工确认。即便增加一次模型审查，也不能宣称形式化证明已理解全部需求。

## 2. 完成检查复用真实回执，防止验收弱化

复用 `invariants.evaluate_criteria()` 已有的执行回执、验证器版本、输入摘要及证据归属检查。

- 机器事实由代码判定：实际执行、输出收集、方法/输入绑定、已执行验证器的结果。
- Agent 评价保留：解释证据意义、比较假设、说明研究局限。不能凭人工评价替代 requirement 已要求的机器证据。
- `revise_gate` 可以改变计划细节、增加检查、替换等价验证路径，但不能删除 requirement 的最低验收要求。对等价性没有已注册规则时，不能仅凭一句理由自动认定等价。
- `completion_exemption` 不能免除用户明确要求的计算或交付；确实无需计算的分析/整理节点可以正常完成。
- 关闭节点、验收要求、终止 checkpoint、doctor 使用共同检查函数，避免 UI、JS 工具和 Python State 各自制定规则。

不采用“Attempt 数量大于零就算做过”的规则。一个 `true` Job、无关分子的结果或过期回执都不能满足本任务的计算证据要求。检查必须绑定输入对象、任务类型、方法参数及当前产物版本。

首批化学验收只覆盖已实现并有测试的证据类型；尚无机器验证器的科学判断明确标注为 Agent 评价，不能包装成自动科学验证。

## 3. 区分工作完成、科学结论与停止依据

优先利用现有 Node/Claim 分离，不为每种失败增加一套独立状态机。

| 情况 | 处理 |
| --- | --- |
| 尚未生成输入 | 保持待执行；生成输入属于下一步工作 |
| 探测或执行证明必要能力不可用 | 对受影响范围记录 blocked 和诊断回执；保留未履行要求 |
| 完成约定分析但无法确定机制 | Node 可 completed，Claim 为 inconclusive |
| 已尝试但未完成约定分析 | 记录具体失败、剩余工作和停止依据，不称交付完成 |
| 用户取消、授权预算耗尽 | 允许停止并保留来源；不要求为了计数启动 Job |

提前停止增加结构化依据：原因类别、匹配作用域的证据/用户事件/预算记录、未完成 requirement、可继续的独立工作。普通目录不存在不能证明 Gaussian 不可用；“尚未执行”本身也不能证明科学问题无解。

会话终止与任务成功分开表达。合法的失败、取消或部分完成可以结束本轮运行，但终态摘要必须保留未履行要求；不通过把所有节点关闭来制造“已完成”。这也避免为了禁止过早退出而引入无限重试。

## 4. 依赖采用明确条件，并共享一处判定

将依赖条件明确为成功完成、已结束等有限类型。成功结果交付默认要求成功完成；阶段性失败通知可接受指定的失败或无结论结果。

仅增加依赖类型不能解决 t008 的漏写依赖。报告和成功交付要显式声明 `consumes`，指向所消费的 requirements、结果及其版本，由代码据此生成或核对依赖；空列表不能默认解释为独立通知。尚未结束的 blocked 节点也不应被当作已结束，阻塞通知应绑定具体状态快照。

实现一个纯 `dependency_evaluation(context, node)`，供 liveness、准入、节点关闭、最终不变量检查共同调用。结果包含依赖 ID、实际 state/outcome、要求的条件与未满足原因。t009 的报错应直接显示“实际 closed/inconclusive，要求 closed/completed”。

注意两个边界：

1. 不允许通过标记前置节点假 completed、删除依赖或任意豁免来发信。
2. `finished` 边不能自动绕过全局 blocked/terminal。正常流程可先发送已授权的状态通知，再记录最终 checkpoint；已有终态的恢复使用显式恢复流程。若将来支持终态通知，需单独限制到绑定真实状态快照和授权的通知入口，不能放开其它执行。

报告/邮件事件也要与状态一致：`study_completed` 应关联已满足的交付要求；失败或部分结果报告应使用相应事件。对不同通知类型是否发送，遵循用户授权和既定通知策略，不把“允许发送失败通知”变成自动扩大的发送授权。

## 5. 科学验证分层，候选生成补足实际实现

`chemical-input.reaction()` 的全局 `validated` 拆为范围明确的检查：分子图、元素/电荷守恒、map-id 一致性、逐原子氢变化、声明的成断键模式及立体对应。反应类别规则放在化学扩展，通用 State 只检查验证回执及其适用范围。

对 t009 所选直接 DA 假设，检查不能只计数成键：还应核对保留骨架、甲基连接、二烯双键迁移与逐原子氢归属。对其它反应不能一律禁止断键或氢转移，应明确声明预期变换。

输入图验证通过、TS 驻点验证通过、IRC 连通性成立是不同证据。一个反应映射回执不能满足 TS 或机制验证义务。

当前 validator 路径只接受已有计算的收集产物。输入验证器需要按版本化 descriptor 明确允许 `registered_artifact` 输入，仍校验归属、schema、大小、摘要和不可变版本；已有计算产物则继续验证 producer 和最新结果回执。验证器可通过现有 Job 执行，产生真实验证 Attempt，不为输入准备或邮件伪造计算 Attempt。

当前能力事实：

- 已有：单分子初始几何、有限立体枚举、Gaussian XYZ opt/SP、显式 GJF 与若干结果检查。
- 待补：适用于所选候选策略的构象/取向准备、片段组合和原子顺序绑定，以及这些输出到实际 TS 搜索入口的可靠衔接。
- 不应宣称已有：文档所述已注册 `ase.neb@1`；当前代码检索没有对应实现。

第一版选择一条能验证的候选路径落实为 helper，并输出带来源的候选清单；不同时声称完整支持所有 NEB/QST/QBICS 策略。候选生成不自动确认为 TS。收敛失败要保留到具体分支，不能因一个猜测路径不存在就结束所有独立工作。

在现有 Skill/扩展清单中明确指导型与可执行入口，并用打包检查验证脚本存在和参数合同。此清单用于发现能力，不另建领域执行调度器；运行仍走通用 Job。

## 6. 用受管引用代替模型转抄摘要

准备请求由代码保存不可变快照、摘要、输入绑定与工作身份，返回简短的 `prepared_ref`。提交按该引用解析；文件修改必须生成新准备记录，摘要校验继续存在。

短引用不是简短哈希前缀的模糊匹配，也不是每轮会变化的数组序号。它必须在工作区内唯一、持久、类型明确且不可重新绑定。并发提交同一引用仍只能启动一次；重复计算仍要求明确的新工作身份和理由。

Artifact 可以提供同样的稳定工具引用，内部保留完整 ID 和摘要。别名由 State/Evidence Registry 管理，所有受管写入在统一边界精确解析；不存在的引用返回候选记录供重选，不自动模糊纠正，不删证据来让操作通过。

写操作返回新 revision、受影响对象和必要恢复信息，避免每次把整份 State 摘要重新追加到上下文。

## 7. 实施顺序与验收

主要改动位置：

| 位置 | 改动职责 |
| --- | --- |
| `research_state/operation_registry.py`、合同 JSON、Host `tools.mjs` | requirements、覆盖引用、停止依据、依赖条件的单一合同及查询接口 |
| `research_state/agent_workspace.py`、`invariants.py`、`admission.py` | 共用覆盖、依赖、关闭与终态检查；版本更新后的失效判定 |
| `tspi_runtime/validators.py` 与 chemical 扩展 | 输入来源策略、领域验证器、版本化验收与范围明确的回执 |
| `apps/app-server/prepared-job.mjs` 与 Evidence Registry | 不可变准备记录、受管引用、幂等解析 |
| chemical 候选/输入/报告脚本与扩展清单 | 真实可调用的研究步骤、语义明确的验证结果与消费关系 |
| email Skill CLI 与交付合同 | 成功交付/状态通知的准入、事件和回执绑定 |

1. **修正实际判断与诊断**：映射验证范围、结构化依赖错误、精确引用恢复、过期能力文档。以 t008/t009 的原始失败输入为回归材料。
2. **建立任务验收约束**：requirements、覆盖投影、停止依据、Gate 修改约束和统一完成检查。先保证零计算不能被弱 Gate 认可为计算交付，未履行要求不会消失。
3. **补可执行研究路径**：候选 helper、所需化学验证器、阶段与分支计划；随后加入类型化交付依赖和受管请求引用。
4. **验证真实 Agent 行为**：先做隔离回归与受控模型评测，再执行有预算的科学集成验收。单元测试通过不能代替模型是否真的调用这些接口的检查。

必要的正反例：

- t008：摘要/ID 不再要求长串转抄；声明不足的交付计划被覆盖检查指出。
- t009：错误映射不能被晋升成 DA 变换验证；未生成输入返回下一步，而非计算不可用。
- 报告 Gate 通过、零相关计算不能满足机制研究的计算证据要求。
- 把机器 Gate 改成人工评价、空洞豁免、无关 Job 成功都不能降低验收。
- 合法调整研究路径、并行独立分支、复用既有证据仍可推进。
- 已完成分析但 Claim 无结论、真实能力失败、预算结束及用户取消均能如实收尾。
- 成功交付与失败通知分别接受正确依赖状态；未知邮件结果不能自动重发。
- 回执/产物更新使旧验收失效；并发、重启和重试不重复产生效果。

合同变更需要显式版本。旧工作区缺少 requirements 不能被自动视为通过新验收；恢复时应从原始用户消息建立范围并重新评估已有证据，不能静默伪造需求、补上通过状态或重发历史通知。

测试环境遵循 AGENTS.md，全部位于 `/home/iaw/debug/tspi-test-env`，测试服务必须清理。本提案不修改生产会话，不恢复历史计算，不重新发送邮件；真实 Gaussian 计算与真实模型评测需要独立的科学验收；隔离测试不替代这些结果。
